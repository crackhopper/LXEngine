# Command Console Debug Attachment Design

## Context

`lxe_editor` currently renders the command console output by concatenating three
independent text sources into one large read-only text buffer:

- command history entries from `CommandBus`
- console-local system lines
- console-local helper output

That model causes two visible problems in the current editor:

1. scene-click debug output is appended at the very bottom of the console,
   instead of appearing directly under the command record produced by that
   click
2. long console output and long command input do not wrap against the visible
   textarea width in the desired way

The requested change is scoped to the ImGui command console presentation layer.
It should not redefine command semantics, command history ownership, or parser
behavior.

## Goals

- Keep the existing auto-printed command record generated by scene clicks.
- Attach click/pick debug lines directly under the most recent visible command
  entry instead of appending them to a global tail section.
- Make console output wrap against the available visible width.
- Make long command input wrap visually while preserving single-command submit
  behavior.
- Preserve existing history, autocomplete, undo, redo, and clear semantics
  unless this design explicitly changes the presentation.

## Non-Goals

- Do not add a new console logging subsystem separate from `CommandBus`.
- Do not change `CommandBus::HistoryEntry` into a richer UI-specific type.
- Do not add real multiline command submission.
- Do not add `Shift+Enter` newline insertion.
- Do not redesign the surrounding editor layout.

## Approaches Considered

### Option A: Render history entries individually and attach debug lines to the latest visible entry

Store console-local attachment data in `ConsolePanel`, keep `CommandBus`
history as the canonical command record, and replace the single concatenated
output textbox with per-entry rendering.

Pros:

- matches the requested output placement exactly
- keeps command ownership in `CommandBus`
- creates a clean path for future per-entry attachments
- solves wrapping cleanly with explicit rendering instead of one giant buffer

Cons:

- requires `ConsolePanel` rendering refactor
- existing string-oriented tests need to shift toward structural assertions

### Option B: Keep the giant concatenated string, but splice debug text after the last entry during formatting

Pros:

- smaller patch

Cons:

- keeps the brittle all-output-as-one-string model
- attachment ownership stays implicit
- future per-entry behavior will likely require another rewrite

### Option C: Introduce a separate UI log model independent from command history

Pros:

- maximum UI flexibility

Cons:

- duplicates state already represented by `CommandBus`
- too heavy for the requested scope

### Recommendation

Use Option A.

It fixes both requested behaviors without inventing a second command-history
system, and it keeps future console output grouping extensible.

## Architecture

### Data ownership

- `CommandBus` remains the source of truth for executed command records.
- `ConsolePanel` owns UI-local attachment state for visible entries.
- `ConsoleInputController` remains responsible for command input state,
  completion, history browse, and submit.

### Console-local attachment model

`ConsolePanel` should maintain a UI-local mapping from visible command entries
to attachment lines.

The design does not require changing `CommandBus::HistoryEntry`. Instead,
attachments stay in the panel because they are presentation-specific and should
not pollute command replay, undo/redo, or API-level command semantics.

The minimal required behavior is:

- when a scene click already produces a command entry, any related debug line is
  appended to that most recent visible entry
- if no visible command entry exists, the debug line falls back to an
  independent console-local line so that diagnostics are not lost
- `clear` resets the visible-output checkpoint and drops attachment state that
  belongs to entries before the checkpoint

### Rendering model

The output area should no longer be rendered as one read-only
`InputTextMultiline` buffer.

Instead, `ConsolePanel` should render a scrollable child region and draw each
visible command entry in order:

1. `> command line`
2. `result message`
3. zero or more attached debug lines

Completion helper output may remain console-local and visually separate, but it
must not be confused with attached click debug lines. It may render after the
entry list as a helper block because it is not associated with a dispatched
command result.

## Output Formatting

### Command entry format

Each visible command entry renders as:

```text
> command line
result message
debug line 1
debug line 2
```

Rules:

- the command line keeps the `>` prefix
- the result message has no prompt prefix
- debug lines appear directly below the result message for that entry
- blank-line spacing between entries may remain, but attached debug lines must
  stay grouped with their owning entry

### Wrapping behavior

Console output should wrap to the available width of the output region.

This is a presentation requirement, not a text mutation requirement:

- long JSON debug payloads wrap visually
- long result messages wrap visually
- long paths or command text in the output view wrap visually
- no horizontal-only overflow behavior should be required for normal reading

## Input Behavior

### Input widget

The command input should move from single-line `InputText` to a multiline input
widget so long commands can wrap visually inside the available width.

However, this remains a single-command console:

- `Enter` submits immediately
- the input model does not accept real embedded newlines as part of a command
- `Shift+Enter` is not supported as newline insertion behavior

The multiline widget is used only to improve long-command readability and
editing.

### Existing command-input behaviors to preserve

The following behaviors remain unchanged:

- `Tab` completion
- `Up` / `Down` history browse
- `Esc` history-browse cancel
- `Ctrl+Z` command undo dispatch
- `Ctrl+Y` command redo dispatch
- empty trimmed submissions remain no-ops

Implementation may need a small ImGui adapter change for multiline callback
behavior, but the controller contract should remain the same.

## State And Clear Semantics

- `clear` still hides prior visible output without mutating `CommandBus`
  history
- attachments associated with entries before the clear checkpoint should no
  longer render
- new commands after `clear` render normally and may receive new attachments
- helper output should continue following current console-local lifetime rules

## Auto-Scroll Behavior

The console should continue scrolling to the bottom when new visible output is
added.

The trigger set expands to include:

- a newly executed command entry
- a new attachment line appended to the latest visible entry
- new completion helper output

## Error Handling

- If a debug line arrives when there is no visible command entry, render it as
  an independent console-local line rather than dropping it.
- If multiline input callback behavior differs from single-line ImGui behavior,
  preserve submit correctness first and adjust the widget adapter accordingly.
- Long wrapping must not truncate output text content; the requirement is visual
  wrapping, not shortening.

## Testing

### Console attachment coverage

Add or update integration coverage for:

- click-generated debug output appearing immediately under the most recent
  command result
- debug output no longer accumulating only at the global bottom of the console
- `clear` preventing old attachments from remaining visible after the clear
  checkpoint

### Input behavior coverage

Add or update coverage for:

- long command input remaining editable after the multiline widget change
- `Enter` still submitting the current command
- `Tab`, `Up`, `Down`, `Esc`, `Ctrl+Z`, and `Ctrl+Y` continuing to work through
  the input controller

### Existing behavior guardrails

Keep coverage that ensures:

- command history rendering still reflects `CommandBus` history ordering
- click commands still update selection as before
- helper output remains separate from real command history

## Acceptance Criteria

- Clicking in the scene still produces its existing command-console entry.
- When click debug logging is enabled, its debug line renders directly below the
  result message of that newest command entry.
- Debug lines are no longer rendered only as a global tail block at the bottom
  of the console.
- Long console output wraps to the visible output width.
- Long command input wraps visually in the input area.
- `Enter` still submits the command as a single logical line.
- The change does not introduce `Shift+Enter` newline insertion behavior.
- Existing command-input controller behaviors continue working after the widget
  change.
